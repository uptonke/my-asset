# Private performance attribution v1.0
Run `sql/performance_attribution.sql` once in Supabase SQL Editor, then manually run Update Private Performance Attribution. The workflow reads the existing ledger and NAV, reconstructs dated holdings, and only publishes the separate performance_attribution JSONB column through a service-role-only RPC with a compare-and-set ledger/history check. A trigger invalidates the report whenever the underlying ledger or NAV changes. No GitHub JSON output, no change to ledger, weights, or approval. Existing portfolio_db RLS applies to reads; review it separately.

Actual portfolio P&L = ending NAV - starting NAV - recorded external flows. Per-ticker P&L uses historical Close (not dividend-adjusted), signed transaction cash flows and opening/closing holdings, split into native price, FX, interaction, and execution vs close. Asset class aggregates are based on the same rows. Corporate split ambiguity, missing or stale quotes, unrecorded dividends/fees, manual NAV marks, and other discrepancies remain explicit residual, not forced into attribution. Ledger dates assumed end-of-day; market calendar/timezone mismatch may matter. Windows use nearest earlier available NAV snapshot and show dates. No broker-certified realized cost-basis P&L.

Factor attribution uses seven-day actual NAV Modified Dietz intervals, computes TWD and USD returns independently (converting flows on their dates), US daily FF5+Momentum spreads compounded weekly, TW index converted to USD and BTC USD excess returns. OLS with HAC(4) requires at least 52 intervals and full rank. In-sample descriptive only; factor sources may lag NAV, missed weeks excluded, Carino links the latest contiguous covered periods without bridging gaps. USD contributions translated by (1+FX), FX and Dietz conversion bridge retained explicitly. No rolling out-of-sample beta yet.


## Automatic refresh
There is no scheduled NAV writer: the web UI's snapshotToHistory/addHistoryRecord saves history_data. The SQL trigger invalidates the report when ledger/history changes. After successful Update Portfolio Holdings (Tue–Sat 21:30 Taipei) and Weekly Macro Pipeline (Mon 00:30 Taipei), the reusable private attribution workflow checks for a missing/invalidated report, count/date mismatch, unavailable factor source after one day, or report age of at least seven days. Fresh reports are skipped. A shared concurrency group serializes manual/automatic runs. Direct manual dispatch forces a rebuild; no new cron or browser credentials. A new UI snapshot is reflected at the next successful parent run, not instantly. Existing SQL migration required; no new migration. The existing off-site backup excludes the derived private report, which can be regenerated after restore. Other existing backup fields remain unchanged.

### Benchmark policy
The default weights are the existing illustrative VT 60%, 0050 20%, BOXX 10%, GLDM 5%, BTC 5%, not an approved policy. v2.5 computes a parallel comparison using Yahoo distribution-adjusted ETF close series (BTC spot, USD converted into TWD), not an official index TR series. Missing adjusted marks cause exclusions or unavailable status, never unadjusted fallback. Recorded portfolio NAV uses Modified Dietz, historical holdings use raw prices and actual recorded ledger cash, recorded income is in execution/other, missing income stays unresolved. This is a hybrid comparison, not complete security-level dividend attribution. Benchmark resets at each observed NAV boundary, no cross-gap link. Calibration reports opening weight deviations, not backfitted optimal weights. BOXX is USD cash-like, not TWD risk-free.

Optional private policy column attribution_benchmark_policy accepts JSON with approved=true, approved_at (actual timezone-qualified timestamp), effective_date (not before approval date), weights (exact five existing keys, nonnegative and sum 1). Set only after personally approving a prospective policy. The new policy uses observed NAV dates on/after effective_date; price-only legacy report stays unchanged. No policy is pre-approved, no user allocations are committed to public Git. Historical NAV gaps and unknown cash remain research-only.

### Quality gate
v2.6 checks each eligible interval against default 1% maximum absolute opening/closing NAV gap relative to recorded NAV, 0.5 pp absolute method bridge and 1e-6 pp arithmetic identity. Micro cash and subscription proxies are flagged for review. Exclusions, invalid snapshots, unapproved policy, unavailable adjusted data and missing adjacent auto pair are visible. Even a screen pass is NOT broker-certified performance; formal attribution and execution permission remain false. Thresholds are engineering defaults.

### Private backup and recovery
The old plaintext Git commit workflow and destructive legacy restore entry point are replaced. Weekly Sunday 12:00 Taipei backup encrypts the selected core row (ledger, history including captured marks, stock_meta, settings, benchmark policy) with AES-256-GCM plus a canonical SHA-256 integrity check; uploads ciphertext only to private Supabase Storage and downloads/verifies it. No new plaintext files, workflow artifacts, or Git commits. Derived reports and other non-core columns are not archived; rebuild after restore. Same-project Storage is NOT independent disaster recovery: download ciphertext from the private bucket to an independently protected offline location, and store the encryption key separately. Verify locally with python scripts/private_portfolio_backup.py verify-local --file PATH (set PORTFOLIO_BACKUP_KEY securely). To restore from local ciphertext to an existing empty target row in a prepared recovery project, set that project's Supabase credentials and the same encryption key, then run python scripts/private_portfolio_backup.py restore-local-empty --file PATH --confirm RESTORE_EMPTY. Target row ID must match source and all core fields must be empty; no live overwrite. Recovery RPC and readback require exact core-field equality. Live storage permissions, key configuration and empty-target restore are not tested in CI.

Existing public Git history and tracked plaintext backups are not removed by this release. Review repository visibility immediately, secure any existing plaintext backup copies, and separately plan Git history remediation and credential rotation where applicable. Do not assume changing .gitignore or deleting a file revokes previously downloaded copies.

Regime-aware walk-forward reuses fixed v3.0 universe, 126 training observations/21 holding observations, common adjusted TWD marks, illustrative initial weights, existing turnover/asset policy and self-financing trading cost. VOO 63-observation drawdown <= -8% or 21/63 volatility ratio >=1.35 signals RISK_OFF (cost-aware CVaR); otherwise 63-observation trend >=3% with ratio <=1.05 signals RISK_ON (lower risk aversion mean variance); else NEUTRAL (standard mean variance). Fixed thresholds not fitted; train strictly ends before execution; test starts afterward. Compare buy-hold, strategic rebalance, static cost-aware mean variance, regime-aware, factor-budget on same dates. No execution signal. Revised provider data, fixed-universe bias, asynchronous marks and missing taxes/lot costs remain. A failed solve holds drifted weights and reports failure.

Factor risk budgeting has two independent models: actual NAV USD weekly excess-return variance attribution (minimum 52 exactly seven-day observed samples, FF8 plus residual, in-sample, signed correlated-factor Euler shares), and fixed-universe TWD proxy factor optimizer (global VOO, TW relative, AVUV relative, QQQ relative, GLDM, BTC and residual). Proxy regression covariance decomposition reconciles to asset variance. Equal illustrative variance budgets including residual; minimize squared budget deviation with existing bounds and turnover cap, not guaranteed exact equality or global optimum. Factor budget strategy is charged the same modeled costs in walk-forward; objective itself is budget mismatch, not net performance. Latest fold is historical, not current recommended weights. No automatic policy approval or live orders.
